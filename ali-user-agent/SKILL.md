# 阿里用户 Agent

将用户底料转化为能在具体任务中稳定思考、判断和反馈的模拟用户。把 Agent 当作证据约束的假设模型，不把模拟结果冒充真实用户结论。

用户直接说“阿里用户 Agent”即可触发并开始首次调用流程，不要求其记忆或输入技术名称 `$ali-user-agent`。

## 首次调用

尚未完成本任务的资料盘点时，先读取 [references/onboarding-flow.md](references/onboarding-flow.md)，优先询问用户能提供什么信息。最多收集五项必要信息；不要直接生成完整 Agent。

收到文件后，先读取并提取文件中已有答案，不重复询问。提醒用户在提供访谈、交易、CRM 等资料前移除不必要的个人或敏感信息。

若用户没有资料，提供三条路径：

1. 经用户同意后检索行业报告、官方资料、企业案例和竞品资料；
2. 经用户确定平台或同意推荐后，研究公开可访问的社群、评论区或论坛；
3. 不检索，直接建立“假设型用户 Agent”，并明确标记 AI 假设。

需要外部检索时，遵守当前工具的浏览、引用和隐私规则。不得绕过登录、付费墙、访问限制或抓取非公开社群。

## 工作流

1. **盘点底料**：整理用户直接反馈、行为与业务数据、内部经验、已有研究和产品资料。
2. **定义任务**：明确模拟对象、需要 Agent 完成的任务、具体情境和结果用途。
3. **提取证据**：区分事实、用户表达、业务判断、外部资料和 AI 假设。使用 [references/evidence-model.md](references/evidence-model.md)。
4. **选择维度**：只选择会影响当前任务的身份、阶段、经验、资源、决策角色、风险偏好等维度；先推荐，再让用户确认。
5. **检查合理性**：检查标签是否冲突、角色是否可能存在、是否值得为当前任务模拟。证据不足时保留为候选，不伪装成已验证群体。
6. **生成基础画像**：描述主体背景、目标、任务、替代方案、能力、资源、限制和相关决策人。企业或机构场景同时生成组织画像和关键角色画像。
7. **生成心智与行为规则**：提炼关注顺序、决策标准、信任条件、风险、推动、顾虑、暂停和放弃条件。无数据支持时不要编造精确百分比。
8. **设置情境**：写清触发事件、流程阶段、时间/预算/组织限制、输入材料和成功标准。
9. **封装 Agent**：按 [references/agent-schema.md](references/agent-schema.md) 输出完整档案和可直接使用的角色 Prompt。
10. **校准**：用历史案例、真人反馈、行为数据或实验结果检查规则；记录命中、偏差、修改及日期。

## 推理纪律

- 资料中的明确事实优先于通用行业知识，行业知识优先于无依据补全。
- 从“用户说重视某因素”不能直接推出精确权重；只有排序、选择实验或行为数据支持时才给出数字。
- 从一次事件不能直接推出普遍放弃规则。
- 发现相互矛盾的证据时，展示差异并尝试按用户类型或情境拆分，不强行平均。
- 不声称 Agent 具有真实经历、情绪或真实市场代表性。
- 用户要求 Agent 评审新方案时，先声明这是模拟反应，不能替代真人研究或真实实验。

## 关键回答标记

在研究报告、规则解释和重大判断中使用以下标记；沉浸式角色对话可自然表达，但用户追问依据时必须恢复标记：

- `[事实依据]`：数据中可直接观察的事实；
- `[证据归纳]`：由多个样本支持的模式；
- `[业务判断]`：内部人员或专家提供的判断；
- `[合理推断]`：由现有事实推导但未直接验证；
- `[模拟反应]`：当前角色与情境下可能的反馈；
- `[AI假设]`：资料未覆盖，由 AI 补充；
- `[无法判断]`：证据不足。

## 完成标准

最终交付至少包括：Agent 身份与情境、知识边界、目标和任务、决策逻辑、推动/顾虑/暂停/放弃条件、If–Then 规则、表达方式、角色 Prompt、证据映射、待验证假设及测试案例。若关键资料缺失，在标题中注明“假设型”或“待验证”。
